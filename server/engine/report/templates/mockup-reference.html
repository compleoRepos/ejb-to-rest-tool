choix architecturaux

Pourquoi COMPLEO a tranché comme ça.

Une migration n'est pas qu'une translation. À plusieurs étapes, COMPLEO a dû choisir entre plusieurs cibles légitimes. Cette section trace les décisions structurantes pour que le dev qui reprend le projet comprenne le "pourquoi", pas seulement le "quoi".

Pourquoi @Service et pas @Component ou @Bean ?

@Service est sémantiquement plus précis : il indique que la classe contient de la logique métier, pas juste un composant Spring générique. C'est la convention adoptée par les guidelines Spring Boot 3 pour les services applicatifs. @Component aurait été techniquement équivalent mais perdrait l'intention. @Bean nécessite une classe de configuration, ce qui aurait été plus invasif.

Pourquoi REST et pas SOAP/JMS pour exposer les endpoints ?

Le code EJB legacy n'exposait pas directement des endpoints — il était appelé par un servlet XbankingServlet via dispatcher EAI. COMPLEO a interprété cette indirection comme un substitut REST et exposé directement les UseCases en @PostMapping. Si l'usage prod nécessite un protocole différent (SOAP préservé pour compatibilité, JMS pour async), signaler à l'architecte avant intégration — le contrôleur peut être adapté facilement.

Pourquoi conserver le pattern UseCase / pourquoi pas inline dans le controller ?

Le pattern UseCase est mature côté BMCE et les équipes le connaissent. COMPLEO l'a préservé en transformant BaseUseCase.run(envIn, envOut) en méthode de service Spring. Le contrôleur reste mince ; la logique métier reste dans le service. Risque évité : réécrire la logique inline aurait cassé la lisibilité pour les devs qui maintiennent.

Pourquoi nexa-* et pas un autre nommage de modules ?

nexa-* est le préfixe choisi pour la plateforme cible (NEXA-IT × BMCE). Le pattern com.nexa.bmce.* sépare le namespace plateforme du domaine BMCE. Modifiable via la config compleo.target.basePackage dans .compleo/config.yml si une convention différente est requise par CGI/BMCE.

Pourquoi pas de tests Karate/Cucumber, juste JUnit ?

Les tests générés sont du scaffolding JUnit + Mockito minimal pour valider la structure des transformations (controller -> service -> repository). Les tests BDD (Karate, Cucumber) nécessitent une compréhension fonctionnelle du domaine que COMPLEO ne peut pas inférer du code seul. Ces tests doivent être ajoutés par les BAs/QA dans une phase suivante.

Pourquoi la classe Envelope est stubée et pas réécrite ?

Envelope est utilisée par 18 services BMCE sur 19. Sa migration définitive (target : DTO Spring + Jackson) impacte le contrat inter-services. COMPLEO a généré un stub temporaire qui préserve la signature EAI pour permettre la compilation isolée du projet avis-opere. La migration réelle d'Envelope se fait au niveau de la Phase I du programme (Tier 0, ma.eai.commons), pas projet-par-projet. Voir le rapport workspace pour le plan global.
