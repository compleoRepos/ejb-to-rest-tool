## 1. Résumé Exécutif

La version 13.9 introduit un **Re-prompt LLM forcé** qui enrichit les méthodes stub (annotées `@CompleoUnvalidated(severity="STUB")`) avec un bloc commenté `// ─── MIGRATED LOGIC (best-effort) ───` contenant une traduction Spring Boot du code legacy source. Le stub reste actif (`throw CompleoUnvalidatedMethodException`) mais le développeur dispose d'un guide de migration directement dans le code.

**Résultats benchmark E2E :**

| Projet | Stubs détectés | Stubs enrichis | Taux | Critères PASS |
|--------|---------------|----------------|------|---------------|
| interface-credit-jocker | 13 | 12 | 92% | 5/5 |
| avis-opere | 8 | 6 | 75% | 5/5 |
| **Total** | **21** | **18** | **86%** | **10/10** |

## 2. Approche Expérimentale

### 2.1 Méthodologie

L'approche a suivi un protocole expérimental rigoureux :

1. **Extraction de 13 méthodes échantillon** depuis les 2 projets BMCE (3 catégories : logique réelle, pass-through SOAP, wrapper trivial)
2. **5 variants de prompts** testés systématiquement
3. **Mesure objective** sur 4 critères : non-stub, validité syntaxique, logique préservée, qualité globale
4. **Sélection du gagnant** par scoring composite

### 2.2 Résultats de l'Expérimentation

| Variant | Description | Avg Quality | Non-Stub | Valid | Logic | Viable |
|---------|-------------|-------------|----------|-------|-------|--------|
| A | Minimal (stub seul) | 0.58 | 60% | 20% | 80% | NON |
| B | Avec source legacy | 0.72 | 100% | 60% | 100% | NON |
| C | Contexte SOAP explicite | 0.64 | 60% | 20% | 100% | NON |
| D | Best-effort + rationale | 0.92 | 80% | 80% | 100% | NON |
| **E** | **Domain keywords** | **1.00** | **100%** | **100%** | **100%** | **OUI** |

Le **variant E** (domain keywords sectoriels) est le gagnant clair avec un score parfait sur tous les critères.

### 2.3 Clé du Succès — Variant E

Le variant E ajoute au prompt :
- Les **domain keywords** détectés par l'IndustryStandardMapper (BIAN, ACORD, etc.)
- Un contexte **Spring Boot** explicite (annotations, injection, patterns)
- Une instruction de **best-effort** avec rationale pour chaque décision

## 3. Architecture Technique

### 3.1 Module StubRePromptEngine

```
server/engine/migration/StubRePromptEngine.ts
├── scanForStubs()      — Détecte les méthodes @CompleoUnvalidated(severity="STUB")
├── findLegacyBody()    — Localise le code source legacy (fuzzy matching)
├── buildRePrompt()     — Construit le prompt variant E
├── cleanLLMOutput()    — Nettoie la réponse LLM
├── wrapAsComment()     — Formate en commentaires // (pas /** */)
└── process()           — Orchestration principale
```

### 3.2 Intégration dans la Pipeline

Le StubRePromptEngine est invoqué dans `CompleoAgent.ts` après le bloc v12.1 PostGenerationMigrator et avant la phase PHASE_END de MIGRATING_BUSINESS_LOGIC. Il traite les `multiTechFiles` (services SOAP/Servlet).

### 3.3 Matching Fuzzy des Sources Legacy

Pour résoudre le problème de nommage divergent (ex: `AvisOpereGetListIndexService` → `AvisOpereGetListIndexUC`), le module implémente un matching fuzzy :
- Strip des suffixes : Service, Impl, Controller, Bean, WS, Delegate
- Essai des suffixes alternatifs : UC, Bean, WS, Impl, Action, Servlet, Helper

### 3.4 Format de Sortie

```java
    // ─── MIGRATED LOGIC (best-effort) ───────────────────────────────────
    // Source: CreditJockerWebService.selectTirageDECLICGAB
    // Generated by Compleo v13.9 Re-prompt Engine
    // Status: UNVALIDATED — requires human review
    //
    // String creditFileNumber = (String) request;
    // log.info("Debut select tirage declic GAB pour noDoss: {}", creditFileNumber);
    // ...
    //
    // ─── END MIGRATED LOGIC ─────────────────────────────────────────────
    @CompleoUnvalidated(severity = "STUB", legacyRef = "...")
    public ModelFlux selectTirageDECLICGAB(Object request) {
        throw new CompleoUnvalidatedMethodException(...);
    }
```

Le format `//` a été choisi pour éviter les nested `/* */` qui causaient des erreurs de compilation avec le CompileAutoFixer.

## 7. Limitations Connues

1. **3 stubs non enrichis** (14%) — méthodes dont le code legacy source n'a pas été trouvé malgré le fuzzy matching
2. **Qualité variable** — le LLM peut générer du code approximatif pour les méthodes très complexes
3. **Dépendance LLM** — si le LLM est indisponible, les stubs restent non enrichis (graceful degradation)
4. **Temps de traitement** — ~10-18 secondes supplémentaires par projet (appels LLM)
